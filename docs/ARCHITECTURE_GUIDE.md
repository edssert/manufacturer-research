# 쉽게 읽는 구조 안내

이 문서는 프로그래밍에 익숙하지 않은 사용자가 앱과 자료 관리 구조를 이해할
수 있도록 설명한다. 개발자용 세부 내용은
[기술 아키텍처](ARCHITECTURE.md), 실제 명령과 작업 규칙은
[루트 README](../README.md)를 참고한다.

## 이 앱은 무엇인가요?

Sound Systems Index는 여러 프로 오디오 제조사의 스피커·앰프·DSP·소프트웨어·
액세서리 정보를 한곳에서 검색하고 비교하는 웹사이트다. 다루는 제조사는 계속
늘어나며, 현재 목록은 프로그램 파일
[`public/js/core/manufacturers.js`](../public/js/core/manufacturers.js)에 적혀 있다.

앱 서버나 데이터베이스에서 정보를 받아오는 방식이 아니다. 화면에 필요한
제품 데이터, 이미지, 글꼴과 프로그램이 모두 배포 파일 안에 있고 브라우저가
직접 읽는다. 그래서 완성된 파일은 일반 정적 웹 호스팅에서 실행할 수 있다.

## 화면은 어떻게 움직이나요?

- 상단 탭에서 Speaker, Amplifier, DSP, Software, Accessories, Brand를
  선택한다.
- 검색창, 제조사·종류 칩, 범위 슬라이더와 정렬을 이용해 카드 목록을 줄인다.
  띄어쓰기나 하이픈이 달라도 `KS 28`, `ks-28`, `KS28`처럼 같은 제품을
  찾을 수 있다.
- 카드를 선택하면 사진과 사양을 담은 상세 창이 열린다.
- 상세 창의 매칭 앰프나 관련 액세서리를 선택하면 큰 화면에서는 두 제품이
  나란히 열린다. 작은 화면에서는 새 상세로 전환되고 내부 뒤로가기 버튼이
  생긴다.
- 상세나 나란히 보기 상태는 주소의 `#` 뒤에 기록된다. 주소를 공유하면 같은
  화면을 다시 열 수 있고, 브라우저 뒤로가기로 상세 창을 닫을 수 있다.

키보드 사용도 같은 흐름을 따른다. 상단 탭은 방향키로 이동할 수 있고, 상세
창이 열리면 포커스가 그 안으로 이동한다. Tab은 상세 안에서 순환하며,
Escape는 사진 확대 → 오른쪽 비교 화면 → 전체 상세 순으로 한 단계씩 닫는다.
닫은 뒤에는 원래 선택한 카드나 관계 항목으로 포커스가 돌아간다.

## 폴더는 왜 나뉘어 있나요?

| 위치                  | 들어 있는 것                            | 웹사이트 배포 여부 |
| --------------------- | --------------------------------------- | ------------------ |
| `index.html`          | 앱 시작 화면과 보안 정책                | 포함               |
| `public/js/`          | 검색, 탭, 상세, 비교 동작과 제품 데이터 | 필요한 파일만 포함 |
| `public/css/`         | 색, 크기, 배치와 반응형 화면 규칙       | 포함               |
| `public/assets/`      | 가공된 제품 이미지와 글꼴               | 포함               |
| `raw-data/`           | 제조사 원문 문서·원본 이미지와 근거 기록 | 제외              |
| `config/`             | 데이터·자산 검사 기준                   | 제외               |
| `public/tests/`       | 자동 검사 코드                          | 제외               |
| `scripts/`            | 빌드, 검사, 이미지 작업 도구            | 제외               |
| `docs/`               | 프로젝트 설명 문서                      | 제외               |
| `dist/`               | 위 소스에서 만든 실제 배포 묶음         | 배포 대상          |

`dist/`는 결과물이라 직접 수정하지 않는다. 제품이나 화면을 바꾸려면
`public/` 등의 소스를 수정한 뒤 다시 빌드한다.

## 프로그램 코드는 어떻게 나뉘나요?

`public/js/` 아래에는 네 가지 큰 역할이 있다.

### 제품 종류별 코드: `domains/`

각 제품 종류는 다음 파일로 책임을 나눈다.

- `data`: 제품 이름, 사양, 사진 경로, 관계 ID
- `schema`: 어떤 항목을 검색·필터·정렬할지 정한 규칙
- `view`: 카드와 상세 화면 모양을 만드는 함수
- `detail`: 제품 ID와 상세 화면 생성기를 공통 등록소에 연결
- `controller`: 목록 상태를 관리하고 나머지 파일을 조립

Brand처럼 다른 제품 상세로 이동하지 않는 특별한 화면은 일부 파일이 없을 수
있다. 반대로 앰프의 Configuration 표처럼 그룹화와 변형 모델 병합 규칙이
복잡한 기능은 별도 순수 모듈로 분리하고, 화면 파일은 그 결과만 사용한다.

### 공통 규칙: `core/`

주소 해석, 검색 엔진, 제조사 목록, 데이터 형식 같은 앱 전체 규칙이 있다.
특히 URL은 화면 코드를 직접 만지지 않는 전용 해석기에서 먼저 안전하게
분석한다.

### 제품 관계: `relationships/`

제품 ID로 실제 레코드를 찾고 “이 스피커와 맞는 앰프”, “이 액세서리를 쓰는
제품” 같은 반대 방향 목록을 만든다. 상세 등록소도 여기에 있다.

도메인끼리 서로의 파일을 직접 복잡하게 가져오지 않고 이 등록소를 사이에
두므로, 제품 종류가 늘어나도 결합이 급격히 커지지 않는다. 상세 창 안의 관계
클릭도 공통 listener 하나가 처리한다.

### 공통 화면 부품: `ui/`

탭, 필터, 카드 격자, 상세 창, 나란히 보기, 사진 확대, 테마와 모션 설정이
있다. 제품 종류별 코드는 이 부품을 조합해 사용한다.

## 원문과 구조화 데이터는 왜 둘 다 필요한가요?

제품 카드에 바로 쓰는 값은 JavaScript 데이터 파일에 있다. 하지만 숫자만
남기면 나중에 출처를 확인하거나 제조사 문서와 비교하기 어렵다. 그래서
제품을 완료 상태로 등록하려면 두 층을 함께 관리한다.

1. 제조사가 공개한 문서 원본을 `raw-data/official-docs/`에, 원본 사진을
   `raw-data/raw-assets/`에 손대지 않고 보존한다. 그 자료에서 확인한 내용을
   제품별 근거 노트로 `raw-data/raw-specs/`에 정리한다.
2. 화면에서 사용할 값을 해당 도메인의 `data/` 파일에 구조화한다.

조사가 끝나지 않은 항목은 `pending: true`로 명시한다. 완료 항목과 미완료
항목의 수, 출처가 아직 없는 예외, 확인하지 못한 앰프 모델과 관계 차이는
사람이 문서에 따로 복사하지 않고
[`config/data-governance.json`](../config/data-governance.json)에 기록한다.
자동 검사는 이 설정과 실제 데이터·Markdown 경로를 비교한다. PDF/DOCX
본문을 자동으로 읽어 판단하는 검사는 아니다.

이렇게 두 층으로 나눈 이유는
[ADR-0002](adr/0002-source-and-runtime-layers.md), 수치를 문서에 적지 않는 이유는
[ADR-0003](adr/0003-baseline-json-source-of-truth.md)에 있다. 실제 작업 순서는
[원문 수집 SOP](sop/source-intake.md)를 따른다.

## 이미지 원본과 웹용 이미지는 어디에 있나요?

고해상도 원본 사진도 저장소 안에 보관한다. 용량이 큰 파일이므로 Git LFS라는
방식으로 저장되며, 위치는 `raw-data/raw-assets/`다. 웹사이트가 실제로 쓰는
가공본만 `public/assets/img/`에 둔다. PNG, JPEG, WebP 등 파일의 실제 형식을
유지하며 코드에 적은 확장자와 파일 확장자가 같아야 한다.

원본을 저장소 안에 두는 이유는 자동 검사가 "이 웹용 이미지가 정말 저 원본에서
나왔는가"를 해시로 확인할 수 있게 하기 위해서다. 원본이 저장소 밖에 있으면 그
확인이 불가능하다.

자산 검사는 다음을 확인한다.

- 코드가 가리키는 파일이 실제로 있는가?
- 아무 코드도 쓰지 않는 고아 파일이 있는가?
- 내용이 완전히 같은 파일의 현황이 승인된 기준과 같은가?
- 웹용 이미지가 기록된 원본·출처와 해시까지 일치하는가?

이미지 가공 도구는 기본적으로 분석만 하고 파일을 바꾸지 않는다. 먼저 dry-run
결과를 검토한 뒤, 그 결과가 현재 파일과 정확히 일치할 때만 별도의 apply 명령이
허용된다. 배경이나 워터마크처럼 자동 판단이 어려운 이미지는 수동 검수 대상으로
남는다. 중복 이미지도 제품에서 의미가 다를 수 있으므로 자동 삭제하지 않는다.

수상 배지나 기능 설명 문구가 들어간 공식 이미지를 그대로 쓰지 않는 이유와, 예외를
어떻게 기록하는지는 [ADR-0004](adr/0004-runtime-image-content-policy.md)에 있다.

## “빌드”는 무엇을 하나요?

이 프로젝트의 브라우저 코드는 그대로 Vanilla JavaScript ES modules다.
빌드는 코드를 하나로 합치는 과정이 아니라, 공개해도 되는 파일만 골라
`dist/`에 안전하게 복사하는 과정이다.

빌드 도구는 다음을 확인한다.

- 웹 시작 파일이 실제로 불러오는 JavaScript 연결망인가?
- 외부 패키지나 저장소 밖 파일을 잘못 import하지 않았는가?
- 누락 파일이나 심볼릭 링크가 없는가?
- 문서, 원문, 테스트, 개발 설정이 배포 묶음에 섞이지 않았는가?
- 모든 배포 파일의 크기와 SHA-256 해시가 manifest와 같은가?
- 같은 입력을 다시 빌드하면 같은 manifest가 나오는가?

따라서 개발 소스 전체가 아니라 검증된 `dist/`만 배포한다.

## 자동 검사는 무엇을 보나요?

`npm run verify` 하나로 다음 범주를 차례로 검사한다.

- 코드 문법, 작성 규칙과 선택된 파일의 형식
- JavaScript 타입 계약
- 제품 ID, 제조사, 필수 필드와 관계 대상
- 원문 출처 coverage와 승인된 공백
- 검색, URL, 등록소와 데이터 불변성
- CSS 클래스와 중요한 표·반응형 배치
- 이미지·폰트 참조와 완전 중복 baseline
- CSP와 로컬 미리보기 서버 경계
- 탭, 카드, 상세, Split View, 접근성, 관계 이동
- 반복 빌드 결과와 최종 `dist/`

하나라도 실패하면 배포 준비가 끝난 것으로 보지 않는다. 각 검사가 정확히 무엇을
지키는지는 [품질 게이트](quality-gates.md)에 정리되어 있다.

자동 검사가 못 보는 것도 있다. 이미지가 제품을 제대로 보여 주는지, 실제 브라우저에서
화면이 무너지지 않는지는 사람이 확인한다. 그 절차는
[육안 검수 SOP](sop/visual-review.md)와 [브라우저 검수 SOP](sop/browser-review.md)에 있다.

## 자주 쓰는 명령

먼저 루트 `.node-version`과 `package.json`의 `packageManager`에 맞춰 Node.js와 npm 버전을 맞춘 뒤 의존성을 설치한다.

```powershell
npm ci
```

전체 검사와 배포 미리보기는 다음 순서다.

```powershell
npm run verify
npm run build
npm run preview
```

브라우저에서
`http://127.0.0.1:4173/manufacturer-research/`를 연다.

목적별로 일부만 검사할 수도 있다.

```powershell
npm test
npm run test:data
npm run test:audit:assets
npm run verify:dist
```

이미지 관련 명령은 모두 "먼저 계획만 만들고 검토한 뒤 적용"하는 방식이다. 명령과
순서는 [런타임 미디어 SOP](sop/runtime-media.md)에 있다.

쓸 수 있는 명령의 전체 목록은 [`package.json`](../package.json)의 `scripts`에 있다.

## 앞으로 서비스형으로 바뀌면 무엇이 달라지나요?

현재 사이트는 계속 공개 비교 기준선으로 유지한다. 여러 관리자가 제품과 사진을 직접
편집하는 기능은 정적 페이지 안에 비밀번호를 넣는 방식으로 만들지 않는다.

- 제품 사실·관계·승인 기록은 Supabase PostgreSQL이 관리한다.
- 로그인은 Supabase Auth가 담당하지만 실제 앱 역할은 DB가 다시 확인한다.
- 원본 이미지와 문서는 Cloudflare R2에 보존한다.
- 공개 사이트는 DB를 매번 조회하지 않고 검증된 JSON 묶음을 받아 현재 UI로 보여준다.
- 큰 PDF·ZIP·OCR 작업은 웹 요청과 분리된 처리 프로그램이 실행한다.
- Cloudflare Workers와 Hyperdrive는 처음부터 넣지 않고 실제 성능 문제가 확인될 때만 검토한다.

이 구조는 아직 운영 중인 기능이 아니다. 목표 경계는 [서비스 설계도](SERVICE_BLUEPRINT.md),
보안 규칙은 [서비스 보안 설계](SERVICE_SECURITY.md), 실제 진행 순서는
[서비스 이행 계획](SERVICE_DELIVERY_PLAN.md)에 있다.

## 제품을 추가할 때의 순서

1. 제조사 공식 자료 원본을 `raw-data/`의 알맞은 폴더에 보존하고 출처 기록을
   남긴다. 자세한 순서는 [원문 수집 SOP](sop/source-intake.md)에 있다.
2. 해당 도메인의 `data/` 파일에 제품 레코드를 추가한다.
3. 사진 가공본이 있으면 `public/assets/img/`에 넣고 레코드의 경로와 실제
   확장자를 맞춘다.
4. 관계 ID가 모두 등록된 제품을 가리키는지 확인한다.
5. `npm run verify`를 실행한다.

대부분은 데이터만 추가하면 카드, 검색, 필터, 상세 화면이 기존 schema와
view를 통해 나타난다. 기존에 없던 필드나 제품 종류를 추가하는 경우에는
schema, view, detail provider와 테스트 계약도 함께 바꿔야 한다.

## GitHub Pages에는 어떻게 올라가나요?

pull request와 push가 생기면 GitHub Actions가 같은 검사를 실행한다. `main`
브랜치의 검사가 모두 통과한 경우에만 `dist/`를 Pages용 artifact로 업로드해
배포한다. 원문 문서나 개발 파일을 저장소 루트째 공개하지 않는다.

이 동작을 사용하려면 GitHub 저장소의 Pages source 설정이 **GitHub
Actions**여야 한다. npm과 Actions 의존성 업데이트는 Dependabot 설정이
정기적으로 확인하며, 업데이트도 같은 자동 검사를 통과해야 한다. 별도의 보안
워크플로가 의존성 변경 검토와 코드 분석도 실행한다.

배포 직전에 확인할 항목은 [릴리스 체크리스트](release-checklist.md)에 정리되어 있다.
이렇게 배포 범위를 좁게 정한 이유는
[ADR-0001](adr/0001-static-deployment-boundary.md)에 있다.
