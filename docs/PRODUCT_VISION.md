# 제품 비전과 핵심 사용 사례

Sound Systems Index는 제품 목록을 전시하는 사이트가 아니라, 프로 오디오 시스템을
학습하고 설계·조달 요구에 맞는 장비를 근거와 함께 찾는 제품 정보 시스템이다.

## 1. 핵심 사용자 목표

### 제조사별 시스템 학습

- 제조사의 제품군, 세대, 포지셔닝과 공식 시리즈 순서를 이해한다.
- 스피커, 서브우퍼, 앰프, DSP, 소프트웨어와 액세서리 사이의 공식 관계를 따라간다.
- 단일 제품 사양뿐 아니라 시스템 구성, 호환성, 필요한 채널 수와 운용 조건을 학습한다.
- 현행 제품과 단종·대체 제품을 구분하고 모든 판단을 공식 근거로 확인한다.

### 설계·입찰 요구조건 기반 제품 탐색

- 설계도서, 시방서, 제안요청서와 조달·입찰 문서의 요구조건을 구조화한다.
- 출력, 주파수 범위, 지향각, 크기, 중량, 설치 방식, 방수·인증, 네트워크,
  증폭·처리 조건과 같은 요구를 단위가 정규화된 조건으로 바꾼다.
- 각 조건에 대해 제품을 `충족`, `미충족`, `근거 부족`, `해당 없음`으로 구분한다.
- 후보 제품과 시스템 구성을 비교하고, 판정에 사용한 공식 문서·페이지·쪽·표를
  추적할 수 있게 한다.
- 자동 결과는 후보 탐색과 검토 지원이며, 최종 적합성·동등성·입찰 판단을 대신하지 않는다.

### 공공조달 공고 추적과 후보 연결

- 조달청·나라장터 등 공공조달 채널에서 음향 시스템 관련 공고와 첨부 문서를
  주기적으로 수집한다.
- 공고 식별자, 기관, 지역, 일정, 상태, 예산, 분류, 정정·취소 이력과 원문 해시를
  보존하고 같은 공고의 버전을 연결한다.
- 첨부된 시방서·설계도서·내역서에서 음향 요구조건을 추출하되, 원문 locator와
  사람이 검토한 정규화 결과를 함께 보존한다.
- 요구조건을 제품 카탈로그와 대조해 제품·시스템 후보, 충족하지 못한 조건,
  확인이 필요한 근거를 설명한다.
- 공고 수집기는 외부 시스템이고 제품 데이터베이스는 canonical 제품 지식의
  소유자다. 공고 원문이나 추출 결과가 제품 사양을 직접 덮어쓰지 않는다.

### 실제 적용 사례 기반 시스템 학습

- 공연장, 경기장, 예배·회의·복합 공간과 투어링 프로젝트의 실제 시스템 적용 사례를
  별도 데이터베이스화한다.
- 장소 유형, 국가·도시, 객석수·수용 인원, 실내외, 공간 규모, 개관·리노베이션 시점,
  설계사·시공사와 설치 목적을 가능한 범위에서 구조화한다.
- 사용 제품, 수량, 배열·배치, 앰프·DSP·네트워크, 서브우퍼 구성과 운영 목적을
  제품 stable ID에 연결한다.
- 사례마다 제조사 case study, 공연장·설계사·시공사 자료와 공개 문서의 출처를
  기록하고, 확인 사실과 해석·추론을 분리한다.
- “이 규모에는 이 제품이 맞다”는 단정 대신, 유사 조건에서 실제 채택된 시스템과
  차이점을 보여주는 근거 기반 유사 사례 탐색을 제공한다.

### 최신 음향 기술 지식 그래프

- WFS, object-based spatial audio, beam steering, 가변잔향·전자음향 보강,
  능동 음향 제어, 네트워크 오디오와 제조사별 구현을 공통 기술 개념에 연결한다.
- 기술 개념, 제조사 용어, 제품·소프트웨어·프로세서, 필요 구성요소, 적용 사례,
  공식 백서·특허·매뉴얼·교육 자료를 서로 관계로 표현한다.
- 같은 마케팅 용어와 기술적으로 동등한 개념을 구분하고, 지원 여부·버전·제약·근거
  날짜를 기록한다.
- 특정 기술을 지원하는 제품 검색과 그 기술이 실제 적용된 프로젝트 탐색을 모두
  제공한다.

### 브랜드와 제품·기술 연혁

- 브랜드 도메인에서 기업 연혁과 제품·기술 연혁을 별도 타임라인으로 관리한다.
- 기업 연혁에는 창립, 사명·소유구조 변화, 인수합병, 주요 거점·공장·조직 변화와
  공식적으로 확인된 경영 사건을 기록한다.
- 제품·기술 연혁에는 시리즈·제품 출시, 세대교체·후속·단종, 소프트웨어·플랫폼
  버전, 핵심 기술 발표와 대표 적용 사례를 연결한다.
- 화면은 `기업`, `제품·기술`, `통합` 보기를 제공하며 같은 날짜의 사건도 유형과
  출처를 잃지 않는다.
- 정확한 날짜, 연·월만 확인된 날짜, 추정 범위를 구분하고 서로 충돌하는 자료는
  하나로 덮어쓰지 않고 출처별 주장과 검증 상태를 보존한다.

## 2. 제품 원칙

1. 제품명 검색보다 요구조건 검색과 비교를 우선한다.
2. 제조사 표현과 정규화한 수치를 함께 보존한다.
3. 값이 없으면 유사 제품으로 추정하지 않고 `근거 부족`으로 남긴다.
4. 제품 단품과 실제 시스템 구성을 구분한다. 앰프·DSP·프리셋·액세서리 조건을
   포함하지 않은 매칭은 완전한 시스템 적합 판정이 아니다.
5. 현행, 단종, 후속 모델과 지역·색상·설치형 변형을 명시적으로 구분한다.
6. 모든 중요한 사실과 매칭 결과는 출처, 수집일, 검증 상태와 변경 이력을 가진다.
7. 검색 결과는 왜 포함되거나 제외됐는지 조건별로 설명할 수 있어야 한다.

## 3. 필요한 도메인 모델

서비스형 canonical 데이터베이스는 최소한 다음 개념을 분리한다.

- `manufacturer`, `family`, `product_group`, `product`, `variant`
- `attribute_definition`, `product_attribute`, `unit`
- `relation`과 증폭·처리·액세서리·대체품 같은 관계 유형
- `media_asset`, `media_placement`, `source_document`, `source_locator`, `assertion`
- `project`, `requirement_document`, `requirement`, `requirement_set`
- `candidate_system`, `candidate_component`, `requirement_evaluation`
- `procurement_notice`, `notice_version`, `notice_attachment`, `notice_watch_rule`
- `venue`, `venue_space`, `application_case`, `system_deployment`, `deployed_component`
- `technology_concept`, `manufacturer_technology`, `technology_support`, `technology_evidence`
- `organization_event`, `product_event`, `technology_event`, `event_evidence`
- `user`, `role`, `change_request`, `approval`, `audit_log`

요구조건 원문, 정규화한 연산자·값·단위, 적용 범위, 필수 여부와 평가 근거를 각각
보존한다. `unknown`은 `false`와 다르며, `not applicable`과 빈 값도 구분한다.

## 4. 검색과 결과 설명

공개 카탈로그는 제품별 read model과 facet index를 사용한다. 입찰·설계 탐색은
프로젝트별 요구조건을 canonical 속성과 관계에 대조해 다음을 제공한다.

- 전체 요구 충족 여부와 조건별 상태
- 단품 후보와 완성 시스템 후보의 분리
- 빠진 앰프·DSP·액세서리 또는 공식 근거
- 단위를 변환한 비교값과 제조사 원문
- 판정에 사용한 출처 locator와 검증일
- 같은 조건으로 재현 가능한 검색·비교 snapshot

전용 검색엔진은 측정된 성능 문제가 생길 때만 추가하며, 검색 인덱스는 canonical
데이터베이스에서 언제든 다시 만들 수 있는 파생물로 유지한다.

추천은 하나의 점수로 사실과 추론을 섞지 않는다. 최소한 `공고 요구조건 적합도`,
`공식 제품 근거 완전성`, `관계까지 포함한 시스템 구성 가능성`, `유사 적용 사례`,
`검토 필요 위험`을 별도 축으로 보여주고 각 결과가 사용한 데이터 버전을 기록한다.

## 5. 아키텍처 방향

복수 관리자, 권한, 승인, 실시간 편집, 프로젝트별 요구조건과 감사 이력이 필요하므로
운영 canonical write model은 PostgreSQL을 우선한다. 원본 이미지와 문서는 객체
저장소에 두고 해시·권리·출처 메타데이터만 데이터베이스에서 관리한다. Git은 코드,
스키마 migration, 검증 규칙과 재현 가능한 snapshot을 보존한다.

현재 정적 앱은 폐기 대상이 아니라 새 API가 만드는 read projection과 결과를 검증하는
기준선이다. 전환은 [ADR-0006](adr/0006-service-catalog-and-admin-authoring.md)과
[기술 아키텍처](ARCHITECTURE.md)의 현재/목표 경계를 따라 단계적으로 진행한다.

## 6. 성공 기준

- 사용자가 제조사 시스템 관계를 공식 근거까지 따라갈 수 있다.
- 동일한 요구조건 입력은 동일한 후보와 판정 근거를 재현한다.
- 충족 결과에 출처가 없거나 단위가 모호하면 품질 게이트가 실패한다.
- 관리자의 모든 변경과 승인은 복원 가능한 감사 기록을 남긴다.
- 기존 stable ID, 관계, 미디어 해시와 URL deep link가 migration 전후에 보존된다.
- 관련 공고의 신규·정정·취소를 중복 없이 추적하고 원문 버전으로 재현한다.
- 객석수나 장소 유형이 비슷한 사례를 찾되 사실과 추론을 화면에서 구분한다.
- 제조사 고유 기술명이 공통 기술 개념, 지원 제품, 실제 적용 사례와 연결된다.

## 7. 단계적 확장 순서

1. 기존 제품·관계·미디어·출처를 PostgreSQL로 무손실 이관한다.
2. 복수 관리자 편집, 승인, 감사 로그와 원본 미디어 저장을 운영한다.
3. 프로젝트·요구조건 모델과 설명 가능한 제품·시스템 매칭을 도입한다.
4. 공공조달 공고 수집·버전 추적과 검토 가능한 요구조건 추출을 연결한다.
5. 실제 적용 사례와 장소 데이터를 축적해 유사 사례 탐색을 제공한다.
6. 최신 기술 지식 그래프를 제품·문서·적용 사례와 연결한다.
7. 기업 및 제품·기술 연혁을 출처 기반 타임라인으로 공개한다.

각 단계는 앞 단계의 canonical 데이터와 출처 품질 게이트를 통과한 뒤 확장한다.
